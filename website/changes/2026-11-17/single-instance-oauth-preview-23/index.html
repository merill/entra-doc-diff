Single-instance OAuth (preview)

17 November 2026New feature+62 / −0 lines

In brief

The new guide describes preview direct authentication using a shared client ID, blueprint credentials, standard OAuth flows, and no intermediate blueprint token or `fmi_path`. It covers local, ASP.NET Core, sidecar, app-only, OBO, and permission-grant scenarios.

What Entra admins need to know

Administrators adopting this capability must provision the Agent ID, configure blueprint credentials, enable tenant authentication, and grant the required permissions.

Single-instance agent authentication overview (preview)

A single-instance Agent ID (preview) authenticates directly with the client ID it shares with its blueprint. It uses the same authentication-library APIs as a regular application. It doesn't acquire an intermediate blueprint impersonation token or send fmi_path.

The blueprint and Agent ID have different directory object IDs. Configure credentials on the blueprint, grant permissions to the Agent ID, and use their shared OAuth client ID for token requests. A single-instance blueprint has no blueprint principal.

Choose an integration path

!Important

Single-instance agent identities are in preview. This preview is provided without a service-level agreement and isn't recommended for production workloads. Some features might be unsupported or have constrained capabilities. For more information, see Universal License Terms for Online Services.

Choose a walkthrough based on where your agent runs. If you're building a platform that hosts separate agents for teams or customers, follow the fleet guidance.

Authentication requires a provisioned single-instance Agent ID and a tenant enabled for authentication. Successful Microsoft Graph provisioning alone doesn't establish authentication enablement. For setup, see Create a single-instance agent identity.

Sign in a user

Local public clients use authorization code flow with PKCE and no client credential. Confidential clients use a credential on the blueprint. An authentication library handles state, PKCE, token caching, and refresh rather than requiring hand-built protocol requests.

For local sign-in and refresh behavior, follow Sign in users from a local agent. For a front end that calls a hosted agent API, follow Authenticate users to an ASP.NET Core agent API or Authenticate users with the sidecar.

Grant application permissions

Declaring permissions on the blueprint doesn't grant them. An administrator grants application permissions to the agent identity. Browser-based admin consent requires a registered web redirect URI, even for an unattended agent.

For the consent request and assignment verification, see Grant application permissions in the cloud-agent walkthrough. For Microsoft Graph, see Grant application permissions to an agent identity.

Request an app-only token

The standard client credentials flow uses the shared client ID, the blueprint credential, and the resource's /.default scope. It doesn't use an Agent ID override.

Follow Call a custom API with ASP.NET Core for CreateAuthorizationHeaderForAppAsync, or Call a custom API with the sidecar for the corresponding HTTP endpoint. For protocol parameters, see OAuth 2.0 client credentials flow.

Call a downstream API on behalf of a user

OBO exchanges an incoming user access token for a downstream token. The incoming token must target the agent's shared client ID, not Microsoft Graph or another resource. The agent authenticates with its blueprint credential. The downstream API evaluates the user's delegated access.

Two separate grants are required: front-end access to the agent's exposed scope and the agent's delegated access to the downstream API. During preview, grant front-end access through Microsoft Graph as described in Grant the upstream client access.

Follow Call a custom API as a user with ASP.NET Core or Call a custom API as a user with the sidecar. These walkthroughs use standard OBO, without an intermediate blueprint exchange. For protocol parameters, see OAuth 2.0 On-Behalf-Of flow.

Verify access

A successful token response establishes token issuance, not authorization at the API. API authorization depends on a valid signature, issuer, audience, and lifetime, plus the required scope or role. Requests with insufficient permissions are rejected. Tokens, certificate assertions, and private keys aren't safe diagnostic output.

For API-side validation, see Secure a web API with Microsoft Entra ID.
