Use an agent's user account with Microsoft 365

17 November 2026Doc update+81 / −57 lines

In brief

The page now recommends using agent identities with application permissions by default, creating an agent user account only for workloads requiring a user object, such as Teams membership, Exchange mailboxes, SharePoint sharing, or user-based licensing. It also outlines provisioning and access-assignment steps.

What Entra admins need to know

Administrators can avoid unnecessary agent accounts and licenses while ensuring required workload access and delegated permissions are assigned when an account is needed.

Agent's user account impersonation protocol

Agent's user account impersonation enables agent identities to operate with user context through an agent's user account, combining user permissions with autonomous operation. In this scenario, an agent identity blueprint (actor 1) impersonates an agent identity (actor 2) that impersonatesUse an agent's user account (subject) using FIC. Accesswith Microsoft 365

Most autonomous agents should call APIs with their agent identity and application permissions. Create an agent's user account only when a Microsoft 365 workload requires a user object.

An agent's user account is scoped to delegationsa dedicated user identity for the agent. It isn't the signed-in user of an interactive agent. Each account has a one-to-one relationship with an agent identity.

Determine whether the agent needs a user object

ScenarioIs an agent's user account required?Guidance
Call an API that supports application permissionsNoUse the agent identity and app-only access.
Add the agent as a member of a Microsoft Teams teamYesTeam membership is assigned to directory users. See add members to a team.
Give the agent its own Exchange Online mailboxYesA mailbox is provisioned for a user object. See create user mailboxes in Exchange Online.
Share a SharePoint or OneDrive item directly with the agent as a personYesUse the agent's user account as the sharing recipient. See sharing files and folders.
Use a Microsoft 365 service that is licensed per userYesAssign only the licenses required by the service. See assign licenses to users.

Don't create an agent's user account only because the agent runs without a person present. If the target service supports application permissions or workload-specific application access controls, use the agent identity instead.

Provision access

  1. Create an agent's user account and associate it with the agent identity.
  2. Assign the account only the Microsoft 365 licenses it needs.
  3. Add the account to the required team, provision its mailbox, or share the required SharePoint resources by following the service documentation in the preceding table.
  4. Grant the agent identity delegated permissions for the Microsoft 365 scopes the workload requires, such as Mail.ReadWrite or Files.ReadWrite. The agent identity uses these delegated permissions when it authenticates as the agent's user account.

Creating the user object doesn't grant access to a team, mailbox, site, file, or API. Complete the workload-specific assignment separately.
