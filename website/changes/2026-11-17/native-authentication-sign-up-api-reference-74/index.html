Native authentication sign-up API reference

17 November 2026Public preview+250 / −0 lines

In brief

The new reference documents server-driven External ID sign-up with policy-defined attributes, email verification, email/password and email one-time passcode methods, and post-sign-up authentication.

What Entra admins need to know

Administrators should know that application sign-up behavior follows the configured user flow and returned policy requirements. No administrator action is stated.

Native authentication sign-up API reference

[!INCLUDE applies-to-external-only]

[!INCLUDE applies-to-authentication-native]

This reference describes sign-up through server-driven attribute collection. Email-with-password and email one-time passcode sign-up use the same operations and message shapes. For these email methods, the user flow associated with the application selects the sign-up method; the client doesn't select it in the start request.

The examples show email-based sign-up. For existing V1 integrations, use the V1 API reference.

The examples use a tenant-verified custom-domain authority. custom_domain is the authentication domain and tenant is the tenant GUID.

Start sign-up

[!INCLUDE native-authentication-public-preview]

The diagram shows a response-driven sign-up sequence. The user flow determines the sign-up method, and the current response determines which attributes and interactions are required.

:::image type="complex" source="media/native-authentication-v2/native-sign-up-sequence.svg" alt-text="Sequence diagram of native sign-up with response-defined attribute collection, verification, and authorization-code exchange." lightbox="media/native-authentication-v2/native-sign-up-sequence.svg"::: The application starts authorization and follows the returned sign-up link. The service returns the current action and requested attribute descriptors.

While interaction is required, the application either collects and submits the requested attributes or handles the returned challenge, verification, enrollment, or activation operation. Each response replaces the previous action, links, and continuation token.

Submitting email can send a passcode and return a verification action without a separate challenge request. Password collection applies only when required by the configured sign-up method.

At state: continue, the application resumes authorization and exchanges the resulting authorization code for tokens. :::image-end:::

Start authorization, then follow its sign_up link with the returned token:

POST https://{custom_domain}/{tenant}/api/v2.0/signup/start
Content-Type: application/json
Accept: application/hal+json

{
  "continuationToken": "******"
}

continuationToken is a required string. The start response can request email:

{
  "continuationToken": "******",
  "state": "interactionRequired",
  "action": "collectAttributes",
  "attributes": [
    {
      "attributeId": "email",
      "inputType": "text",
      "hidden": false,
      "required": true,
      "canChange": true,
      "label": "Email"
    }
  ],
  "_links": {
    "submitAttributes": {
      "href": "/{tenant}/api/v2.0/signup/submitattributes"
    }
  }
}

Labels, requiredness, and validation metadata come from policy. Use those requirements within your application's interface and collection logic.

Submit attributes

Follow _links.submitAttributes.href. Collection can occur more than once:

POST https://{custom_domain}/{tenant}/api/v2.0/signup/submitattributes
Content-Type: application/json
Accept: application/hal+json

{
  "continuationToken": "******",
  "attributes": {
    "email": "user@contoso.com"
  }
}
PropertyTypeRequiredDescription
continuationTokenString.Yes.Latest sign-up token.
attributesObject of string values.Yes.Values keyed by the exact returned attributeId values.

All required values must be supplied before sign-up completes. Optional values can be omitted. Missing required values can produce a validation error or another collectAttributes response.

For email-with-password sign-up, submit a password when requested. For example, a collection round that requests password and profile fields can accept:

{
  "continuationToken": "******",
  "attributes": {
    "email": "user@contoso.com",
    "password": "******",
    "givenName": "Example",
    "surname": "User"
  }
}

Submit fields according to the user flow's returned descriptors. Email one-time passcode sign-up creates a passwordless account that signs in with an email passcode.

Collection order

The service can request email first, collect several attributes together, or return to attribute collection after verification. Submit attributes requested by the latest response rather than predicting the sequence from the values submitted.

Your app can organize collection according to its flow logic and the available descriptors. See Collection order and email verification. Each response determines the available next operations.

Interpret attribute and page descriptors

Each response describes the current form. The following fields define an attribute:

FieldMeaning
attributeIdSubmission key.
inputTypeInput control type, such as text, password, boolean, date, or checkboxMultiSelect.
requiredWhether a value must be supplied.
hiddenWhether the field is hidden.
canChangeEditability information, when included.
labelOptional display label.
initialValueOptional prepopulated value.
validation.validationRegExOptional validation pattern.
optionsOptional choices with label and value properties.
confirmationInputOptional confirmation behavior, such as retype, reveal, or none.

Don't require a pages member. The current attributes array defines the fields and requirements; page-grouping metadata, if returned, is additional presentation information. Input control types don't change the string-valued submission object. See User attribute concepts.

Verify email

When attribute submission requires email verification, it sends the passcode and returns:

{
  "continuationToken": "******",
  "state": "interactionRequired",
  "action": "verify",
  "id": "{email_method_id}",
  "type": "email",
  "hint": "u***@contoso.com",
  "codeLength": 8,
  "_links": {
    "verify": {
      "href": "/{tenant}/api/v2.0/auth/methods/email/{email_method_id}/verify"
    },
    "resend": {
      "href": "/{tenant}/api/v2.0/auth/methods/email/{email_method_id}/challenge"
    }
  }
}

The service has already sent the passcode; proceed directly to verification. Use the returned length and masked hint. Post to verify:

POST https://{custom_domain}/{tenant}/api/v2.0/auth/methods/email/{email_method_id}/verify
Content-Type: application/json
Accept: application/hal+json

{
  "continuationToken": "******",
  "otp": "{one_time_passcode}"
}

To request another code, post only the latest continuationToken to the current resend link, subject to service limits.

Verification can return more attribute collection:

{
  "continuationToken": "******",
  "state": "interactionRequired",
  "action": "collectAttributes",
  "attributes": [
    {
      "attributeId": "givenName",
      "inputType": "text",
      "hidden": false,
      "required": true,
      "canChange": true,
      "label": "First name"
    }
  ],
  "_links": {
    "submitAttributes": {
      "href": "/{tenant}/api/v2.0/signup/submitattributes"
    }
  }
}

Submit the requested values and continue handling the next response.

Complete policy requirements and authorization

After account creation and any required verification, complete any multifactor authentication (MFA) and Conditional Access requirements before resuming authorization.

If the response advertises another method challenge, use the shared challenge and verification operations. Method registration is distinct from verifying a sign-up email. See Method discovery and registration for the enrollment contract.

When the service returns state: continue, follow _links.continue, resume authorization, and exchange the code. This acquires tokens without starting an unrelated sign-in transaction.

Errors and lifecycle

Use the shared error envelope. Structured validation entries can contain code, message, attributeIds, suggestions, and optional recovery.

ConditionStatus or behaviorHandling
Invalid continuation token400Restart the flow.
Missing or invalid attribute400 or another collectAttributes responsePresent field-level feedback and submit corrected values.
User already exists400 invalidRequestOffer generic sign-in or recovery guidance without unnecessarily disclosing account existence.
Password policy violation400Collect a compliant password.
Incorrect email passcode400 invalidGrant with innerError.code: invalidOneTimeCodeLet the user correct the code using the usable current state or an advertised resend.
Missing passcode400 invalidRequestCorrect the missing input.
Throttling429Honor server retry guidance.
Unsupported native interactionstate: redirectStop native requests and offer the configured browser path or a clear failure.

Handle other failures through their actual status and stable error codes. Don't treat an expired transaction as a recoverable incorrect-code entry.

Attribute submission isn't idempotent after user creation. Don't replay successful submissions, log sensitive attribute values, or treat client-side validation as authoritative.
