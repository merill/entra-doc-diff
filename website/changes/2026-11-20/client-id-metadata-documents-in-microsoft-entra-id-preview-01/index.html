Client ID Metadata Documents in Microsoft Entra ID (preview)

Client ID Metadata Documents (CIMD) are a new way to register OAuth clients with Entra ID. CIMD is primarily used by AI agents that need to connect to remote MCP servers.

!Important

Client ID Metadata Document support in Microsoft Entra ID is in public preview. This preview is provided without a service-level agreement and isn't recommended for production workloads. Some features might be unsupported or have constrained capabilities. For more information, see Universal License Terms for Online Services.

Why CIMD

AI agents may use many different MCP servers to perform work. Some of these MCP servers may be secured by Entra's OAuth server — e.g. WorkIQ, Azure Storage MCP, or enterprise-built MCP servers. Others may be secured by a different OAuth server — e.g. GitHub, Workday, Slack. For general purpose AI agents, it's impractical to know all MCP servers it will use, and therefore impractical to know all OAuth servers the AI agent will encounter. The AI agent needs a way to dynamically register itself with an OAuth server and obtain a client ID.

Client ID Metadata Documents (CIMD) let an OAuth client identify itself by using an HTTPS URL as its OAuth client_id value instead of a preassignedpre-registered client ID. TheA JSON document at that public URL contains the client's OAuth metadata. Microsoftmetadata, such as its redirect URIs and client credentials. CIMD is useful when a client must connect to many authorization servers with which it has no prior relationship. For example, an MCP clientAI agent can discover remote Model Context Protocol (MCP) servers at runtime, and each server might use a different authorization server. Requiring every client to be registered with every authorization server doesn't scale.

CIMD is defined by the OAuth Client ID Metadata Document specification. The MCP authorization specification recommends CIMD for clients that don't have another supported registration mechanism.

  • No app-only tokens: CIMD clients can't use the client credentials grant.
  • Audience restriction: Microsoft Entra ID doesn't issue tokens whose audience is the CIMD client.

Consent and permissions for clients using CIMD

UnderEntra treats clients using CIMD as unverified, and honors existing tenant consent policy. This means that the default recommended consent policy,following rules apply:

Tenant SettingWhat users can consent to
Default consent policyUsers can sign-in to CIMD clients. This creates an agent identity in the tenant. Users can only grant a very limited set of OAuth scopes to low-riskCIMD clients, such as openid and User.Read in Microsoft Graph. Risk-based step up prevents users from granting any other permissions to CIMD clients.
Do not allow user consentIn tenants that have disabled user consent via the Do not allow user consent setting in Entra Admin Center, users cannot consent to CIMD clients. This means they cannot add CIMD clients to their tenant, nor can they grant OAuth permissionsscopes to CIMD clients.
Other consent policyUsing consent policy, tenants can allow users to consent to CIMD clients. Administrators have fine-grained control over the conditions when user consent is allowed.

Admin controls for CIMD clients. Sensitive

Tenants can prevent users from adding CIMD clients or granting them new permissions require administrator consent. For administrator guidance, see Manage CIMD clients in Microsoft Entra IDvia consent policy. Use either of these approaches:

  • Block all user consent, via the Do not allow user consent setting in Entra Admin Center.
  • Allow user consent only for apps from verified publishers.

Either of these policies will prevent non-admin users from adding CIMD clients to a tenant. Follow Manage app consent policies to configure consent policy in your tenant.

To enable the use of a specific agent or client using CIMD, administrators can individually add agent identities to their tenant by providing the CIMD URL. This can be done via Entra Admin Center or Microsoft Graph APIs. See Managing CIMD clients.

Governance considerations

  • Entra doesn't provide a tenant-managed domain allowlist or blocklist for CIMD URLs.
  • Losing control of the document URL or its domain can affect every tenant that trusts that client identity.

UseAlways use least-privilege delegated permissions, preapprove clients that need sensitive access, monitor their sign-ins, and remove identities that are no longer required.
